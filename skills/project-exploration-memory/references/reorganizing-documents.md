# Reorganizing memory documents

This procedure uses the six public tools: `project_memory_catalog`, `project_memory_details`, `project_memory_write`, `project_memory_edit`, `project_memory_history`, and `project_memory_retire`. A write replaces the current document at the supplied slug; retirement is explicit: `archive` preserves the complete document as readable historical content and denies later mutation, while `supersede` deletes the target only after every replacement has been verified, with best-effort cleanup and no cross-file rollback guarantee. There is no rename operation.

## Shared preparation

1. Call `project_memory_catalog` without guessing slugs. Select candidates from their business-facing titles and descriptions, then call `project_memory_details` for every candidate. Read older `project_memory_history` pages when the recent reasons do not explain why documents were separated or combined. Repeated co-reading is only a signal: merge when one coherent business-function explanation is genuinely clearer. Auth plus checkout, for example, need not merge merely because they are often read together.
2. Inspect the relevant current source before choosing any canonical slug. Map the implementation's function boundaries and source-backed claims, using the documents only as hypotheses and resolving stale or incomplete memory against the code. A split is justified by independent business or subfunction responsibility, not by document size or retrieval telemetry. Keep the business-unit rule: one document should normally explain one business function, with its implementation, actors, outcomes, authorization, durable changes, and boundaries.
3. Choose the canonical slug or slugs only after that inspection. Reuse an appropriate existing slug where that preserves the established retrieval path; choose a new slug only for a genuinely new business or subfunction boundary.
4. Compose the complete replacement narrative from current, source-backed facts. Use supported source anchors beside claims and submit anchors plus ordinary prose, not copied generated evidence; see [persistence and evidence details](persistence-and-evidence.md). Do not overwrite an old document with a shortened draft until the destination is verified.

## Shared execution rule

Publish each new or replacement destination one at a time. After each publish, use expanded `project_memory_details` to verify current evidence and completeness; then, where supported, use a fresh editable read immediately before each exact edit to update known controllable links, source-document references, and catalog metadata. Only after those supported updates and destination checks may you shorten or retire an absorbed original. This updates only references you can identify and control; do not promise discovery or revision of arbitrary external references or macros.

## Merge procedure

1. Catalog and read all source documents and, as needed, their history; list the claims, boundaries, and links that the merge must retain. Identify any old-slug references you know about, but do not assume arbitrary external references can be found or updated.
2. Inspect the current implementation sources relevant to the merge and map their function boundaries and claims. Use this inspection to confirm or correct the boundaries inferred from memory before selecting a destination slug.
3. Choose the canonical existing slug (or a new slug only if the merge establishes a genuinely new boundary). Prepare one coherent, non-duplicative document for that slug. Preserve distinct business boundaries in explicit sections when they remain separate; do not turn related functions into one narrative just because they are commonly retrieved together.
4. Before publishing, use fresh source reads and an editable details read for any existing destination that will be edited. Submit `project_memory_write` for a new destination or a full replacement, or `project_memory_edit` for targeted changes. Set a discoverable title and description naming the canonical function and scope. The write/edit expands inspected anchors and records a reason; it does not publish a batch.
5. Verify the destination with `project_memory_details` (including freshness and expanded evidence) and, when useful, `project_memory_catalog`. Confirm that the content is complete, the anchors are current, and the title/description identify the canonical slug. Then, with a fresh editable read immediately before each exact edit, update known controllable links, source-document references, and metadata as appropriate. Only after those supported updates may you shorten an absorbed original or turn it into navigation/compatibility material.
6. For each absorbed old slug, use `project_memory_details` with `view: editable` immediately before `project_memory_edit`, then replace its full explanation with a short stub or retained overview. Change its title and description explicitly to say `Navigation/compatibility stub — canonical: <slug>` (or `Overview — canonical documents: <slugs>`), and make the body say that the old slug is not the canonical explanation and ordinary retrieval should use the named canonical slug(s). A stub is an ordinary document, not an automatic alias or redirect: old references do not transparently receive the new content, and no recursive macro should be used to imply following. If historical access is required, use `project_memory_retire` with `mode: "archive"` after the destination is verified; use `mode: "supersede"` only when the replacement slugs are verified and the old content is intentionally removed. Report any best-effort partial failure; never edit managed artifacts directly.

## Split procedure

1. Catalog and read the candidate document, its history when the boundary is unclear, and relevant neighboring documents. Identify the candidate claims and boundaries, but do not split merely because the document is large or frequently retrieved.
2. Inspect the current implementation sources and map the function boundaries and claims that belong on each side. Use current source behavior to confirm or correct the boundary inferred from memory before selecting slugs.
3. Choose the canonical slug for each resulting function only after that inspection. Reuse the original slug for the function that best matches its established purpose when useful; use a new slug for an actual new boundary. Prepare complete, non-duplicative narratives, with each claim supported by freshly inspected source anchors. If a short overview is useful, define it as navigation/compatibility rather than another full business-function narrative.
4. Keep the original's full content intact while publishing every other/new destination one at a time with `project_memory_write` (or an exact `project_memory_edit` after a fresh editable read). After each publish, verify that destination through expanded `project_memory_details` and current evidence. Do not shorten the original while any other split destination is incomplete, unverifiable, or stale.
5. After all other/new destinations are verified, use fresh editable reads immediately before each exact supported edit to update known controllable links, source-document references, and catalog metadata as appropriate. Only then edit the original using another fresh editable details read: retain its full explanation narrowed to its remaining function, or replace it with a clearly labelled `Navigation/compatibility overview — canonical: <slug-a>, <slug-b>` whose body briefly states the boundary and directs ordinary retrieval to those slugs. It must not repeat competing full explanations. Known old references may remain and arbitrary external references cannot be promised updated.
6. Verify the final catalog and each destination/original with `project_memory_details`. If any destination failed, preserve the untouched original, stop additional shortening, inspect and report the actual catalog/details and which slugs are verified; do not claim an atomic multi-document publish or rollback.

## Failure and compatibility boundary

Each write or edit is a separate publication. If a mutation fails or returns an integrity warning, preserve untouched documents, stop additional shortening, inspect and report the actual tool results and which slugs are verified, and do not claim rollback or automatic repair. A safe ordinary later write may correct a readable state when the actual contracts permit, but do not promise a blanket resume or repair. `project_memory_retire` has the same controlled-failure boundary: archive preserves historical content, while supersede removes a target only after verified replacement preconditions and may leave a reported partial cleanup.

Old slugs have precise supported fates: retain the original as a canonical document, replace it with a clearly labelled navigation/compatibility stub or overview, archive it as preserved historical content, supersede it after verified replacement preconditions, or leave it unchanged and report that cleanup is not safe. An archived document remains readable but is mutation-denied; supersede intentionally removes the target and does not provide rollback or transparent compatibility for old references. A stub is not an alias, redirect, or transparent compatibility layer for old references. Never promise that old references, including known macro references, are automatically discovered or rewritten. If preserving full old-content compatibility is required, or if safe supersede cannot be verified, stop and ask for a user decision rather than hand-editing managed state or claiming removal.
